# NARRAY機能グループ: 二次元配列の診断と資源境界

> 本文は現行実装の規範契約です。
>
> [二次元配列仕様](nested-arrays.md)と[適合性](nested-arrays-conformance.md)に従います。

## 1. 診断方針

NARRAY機能グループは既存配列診断を二次元へ一般化し、1二次元値の論理葉要素上限に1コードだけ追加します。
静的診断は既存どおり終了8または9、実行時資源診断は重要度error、終了10です。

## 2. 既存診断の継続・拡張

| コード | NARRAY機能グループの意味 |
|---|---|
| `E_EXPECTED_ARRAY_ELEMENT_TYPE` | 内側・外側の型引数が欠落 |
| `E_EXPECTED_ARRAY_TYPE_END` | 任意階層の閉じ`>`が欠落 |
| `E_ARRAY_ELEMENT_TYPE_REQUIRED` | bare `配列`を具体型として使用 |
| `E_EMPTY_ARRAY_TYPE_REQUIRED` | 内側または外側の空literalから型を推論できない |
| `E_ARRAY_ELEMENT_VALUE_MISSING` | 任意階層の要素式が0値 |
| `E_ARRAY_ELEMENT_VALUE_COUNT` | 任意階層の要素式が2値以上 |
| `E_ARRAY_ELEMENT_TYPE_MISMATCH` | 同じ容器の要素型が完全一致しない |
| `E_ARRAY_ELEMENT_CALL_NOT_ALLOWED` | 入れ子要素式から禁止呼出し |
| `E_ARRAY_ELEMENT_NOT_ALLOWED` | 入れ子要素式に制御・宣言・代入 |
| `E_NESTED_ARRAY_NOT_AVAILABLE` | 三次元以上の配列型または値 |
| `E_ARRAY_ELEMENT_TYPE_NOT_ALLOWED` | ラッパー外に直接置かれた禁止要素型 |
| `E_ARRAY_LOOP_INPUT_UNDERFLOW` | 任意階層の配列loop入力不足 |
| `E_ARRAY_LOOP_INPUT_TYPE_MISMATCH` | loop入力が配列でない |
| `E_ARRAY_INDEX_OUT_OF_BOUNDS` | 外側行または内側要素の添字不正 |
| `E_ARRAY_RANGE_OUT_OF_BOUNDS` | 外側または内側の半開区間不正 |
| `E_ARRAY_LENGTH_LIMIT` | 1容器の直接要素が65,536超 |
| `E_ARRAY_CONSTRUCTION_LIMIT` | 1実行の直接要素参照構築が1,000,000超 |
| `E_ARRAY_ELEMENT_OPERATION_LIMIT` | 1実行の訪問直接要素参照が10,000,000超 |

`E_NESTED_ARRAY_NOT_AVAILABLE`のコードは維持し、旧来の二次元拒否caseを三次元拒否caseへ置き換えます。
message、expected、actual、fixは「二次元まで利用可能、三次元以上は未対応」を表します。

`任意<T>`と`結果<T,E>`は配列要素にできます。ラッパー越しの配列構築子も数え、合計3個以上なら
`E_NESTED_ARRAY_NOT_AVAILABLE`です。ラッパー外に直接置くことを許可していない既存型には、引き続き
`E_ARRAY_ELEMENT_TYPE_NOT_ALLOWED`を使います。

## 3. 新規診断

| コード | 条件 | 必須fields |
|---|---|---|
| `E_ARRAY_NESTED_ELEMENT_LIMIT` | 1二次元値の論理葉要素合計が1,000,000を超える | `word`または`operation`、`limitName=arrayNestedLeafElements`、`limit`、`observed` |

リテラルでは上限を超えることが確定した最初の外側要素、外側の追加・置換・一部取得では操作語を主位置にします。
`observed`は上限+1で飽和させず、64 bit符号付き範囲内で正確に計算できる場合は正確値を返します。
加算overflowを起こす合成内部値は内部エラー70です。

## 4. 型構文と静的診断順

配列型は次の順に検査します。

1. `配列`直後の`<`
2. 要素型の存在
3. 内側型の構文と閉じ`>`
4. 外側の閉じ`>`
5. 型構築子深さ256
6. 配列次元2
7. 葉型の配列要素許可

欠落記号から次元、葉型、名前診断を派生させません。三次元かつ葉型不許可なら、外側から走査して先に
確定する三次元超過を1件報告します。

## 5. リテラル診断順

各階層で既存の構文回復を行った後、次の順です。

1. 要素式の許可構文・呼出し
2. 各要素式が残す値数
3. 最初の要素からの完全な型一致
4. 配列次元2
5. 1容器の直接長65,536
6. 外側二次元値の論理葉合計1,000,000
7. 構築・要素処理予算
8. 出力stack

`【【】】`は内側の型なし空literalだけを報告し、外側の型不一致や次元診断を派生させません。
葉型の異なる行では、行長や論理葉上限より型不一致を優先します。

## 6. 既存操作の判定順

外側配列の5操作は、入力型、添字・範囲、1容器長、候補論理葉合計、構築・要素処理予算、stackの順です。

- 長さ・1行取出しは論理葉合計を変更しない
- 一部取得は対象行の葉数合計を検査する
- 行置換は`元合計 - 旧行長 + 新行長`を検査する
- 行追加は`元合計 + 新行長`を検査する
- 内側一次元操作は既存ARRAY機能グループの順序を変えない

拒否された予約は加算しません。条件をすべて通るまで入力スタック、元の内外配列、保存値、両出力を
変更しません。

## 7. 等価性、表示、反復

等価比較は型、外側長、対応行長を検査し、比較候補の外側参照数と論理葉数を要素処理予算へ予約してから
走査します。最初の不一致で実走査を停止しても、予約済み予算は戻しません。予算拒否では入力2値を保ちます。

表示は候補UTF-8長と訪問要素数をcached metricsから有限幅で求め、表示上限、要素処理予算、stdout能力の順に
検査してから1回で書きます。部分出力しません。

外側・内側反復は各要素を渡すごとに既存の要素処理単位を使います。空外側と空行は本体0回です。
loop stack診断、`打ち切る`、`続ける`の原子性は既存規則を維持します。

## 8. traceと非開示

NARRAY機能グループで許可する葉型は既存のtrace方針に従います。通常traceは各階層8要素で打ち切り、値全体の
logical leafを走査しません。JSON葉を持つ二次元配列は既存の推移的非開示により値全体を伏せます。

診断`dataStack`は既存配列方針を再帰適用します。診断message・fieldsへ配列全内容や巨大表示を入れず、
型名、次元、添字、長さ、規範上限、論理葉数だけを公開します。

## 9. 内部境界

次は利用者診断へ変換せず内部エラー70です。

- `ArrayType`と`ArrayValue`の要素型不一致
- 三次元以上または不許可葉型を持つ合成値
- 直接長、logical leaf count、cached表示長の不一致
- 負数、overflow、上限超過を持つ構築済み内部値
- `BuildArray`の宣言型・要素数・実stack不一致

適合試験は公開caseとは別に、合成IRとpackage内runtime構築で各防御境界を固定します。
