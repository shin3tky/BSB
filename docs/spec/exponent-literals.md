# EXP機能グループ: BSB数値リテラルの指数表記

> 本文は現行実装の規範契約です。
>
> 本仕様はD-030の「指数表記を初期仕様では受理しない」という機能境界をEXP機能グループで変更します。
> CORE、NUM、TEXT機能グループの規則は、ここで明示的に変更する箇所以外、引き続き有効です。
>
> 現行契約: DTXT機能グループの[小数文字列の指数表記](decimal-text.md)が、
> 本文の「文字列変換は指数を拒否する」というEXP機能グループの非変更境界を上書きします。

## 1. 範囲

EXP機能グループでは、BSBソースの数値リテラルへ10進指数表記を追加します。
新しい値型、演算、組み込み語、暗黙変換、2進浮動小数、16進浮動小数、`NaN`、無限大は追加しません。
文字列からの数値変換とJSON数値の文法・実装は、それぞれTEXT、JSON機能グループの独立した契約です。DTXT機能グループは、このうち小数文字列変換だけを別契約として拡張します。

この変更によって、従来`E_INVALID_NUMBER_LITERAL`だった`1e3`は有効な`小数`リテラルになります。
外部公開版としての後方互換性はまだ保証していないため、言語版フラグは追加しません。

## 2. 字句文法

```text
digit          := "0" | "1" | ... | "9"
nonZeroDigit   := "1" | ... | "9"
integerPart    := "0" | nonZeroDigit digit*
fraction       := "." digit+
exponent       := ("e" | "E") ("+" | "-")? digit+

integerLiteral := "-"? integerPart
decimalLiteral := "-"? integerPart (fraction exponent? | exponent)
```

指数記号はASCIIの`e`または`E`です。指数部だけは任意の`+`または`-`を持てます。
リテラル全体の先頭に`+`は書けません。指数部の先頭0は許可し、`1e002`は有効です。

正常例は`1e2`、`1E2`、`1e+2`、`1e-2`、`1.5e3`、`-0e10`です。
`+1e2`、`01e2`、`.5e2`、`1.e2`、`1e`、`1e+`、`1e-`、`1ee2`は不正です。
数字から始まらない`e2`は数値候補ではなく識別子として走査します。

数値候補は区切りまで最長一致で読みます。完成した指数表記の直後に識別子文字が続く
`1e2円`は`E_MISSING_SEPARATOR`、指数部が未完成な`1e円`は`E_INVALID_NUMBER_LITERAL`です。

## 3. 型と値

指数部を持つリテラルは、小数点がなく、数学的な値が整数でも、常に`小数`です。
したがって`1`は`整数`、`1.0`、`1e0`、`100e-2`は`小数`です。整数と小数の暗黙変換は行いません。

仮数の小数点を除いて得た符号つき係数を`c`、小数部の数字数を`f`、符号つき指数を`p`とすると、
リテラルの値と構築前スケールは次です。

```text
値              = c × 10^(p - f)
構築前スケール  = f - p
```

値は丸めず、NUM機能グループの正確な`小数`へ変換します。その後、0を標準化し、0以外の係数末尾0を除去します。
`-0e10`は`0.0`、`1.500e2`は`150.0`、`1e-2`は`0.01`になります。

## 4. 資源上限と安全な構築

数値リテラルの入力数字は従来どおり4,096個までです。整数部、小数部、指数部に現れる
ASCII数字を、先頭0と末尾0を含めてすべて数えます。先頭符号、小数点、指数記号、指数符号は数えません。

指数値は有限幅で飽和させながら走査し、次をこの順に検査します。

1. リテラル全体が第2節の文法に一致するか
2. 入力数字が4,096個以下か
3. 構築前スケール`f - p`の絶対値が65,536以下か
4. 正規化後スケールの絶対値が65,536以下か
5. 上限内と確定してから、係数とスケールを持つ小数値を構築できるか

3は、値が0で正規化後スケールが0になる場合にも適用します。したがって`0e65536`は有効、
`0e65537`は`E_DECIMAL_SCALE_LIMIT`です。`10e65535`は正規化後スケールが`-65536`で有効ですが、
`10e65536`は正規化後スケールが`-65537`なので同じ診断です。

入力数字上限により、リテラルから作る正規化係数の有効桁は65,536を超えません。
この経路で`E_DECIMAL_RESULT_PRECISION_LIMIT`は発生しません。巨大な指数を`Integer.parseInt`、
無検査の`BigDecimal(String)`、固定小数点の巨大中間文字列へ直接渡してはなりません。

## 5. 表示とフォーマット

実行値の表示、数値から文字列への変換、診断プレビュー、トレースはNUM機能グループの正規表示を維持します。
指数は使わず、小数点を必ず含め、数学的な整数には`.0`を付けます。

| 入力字句 | 実行値表示 |
|---|---|
| `1e2` | `100.0` |
| `1E-2` | `0.01` |
| `1.500e3` | `1500.0` |
| `-0e10` | `0.0` |

`format`は値の正規化を行わず、有効な数値字句をバイト単位で保持します。`e`と`E`、指数の`+`、
指数部の先頭0、仮数の末尾0を変更しません。したがって`1E+02`は`1E+02`のままです。
構築前・正規化後スケールの検査は値を必要とする`check`と`run`で行い、構文と4,096数字上限を満たす
`1e65537`を`format`だけは保持できます。

## 6. 文字列変換との境界

EXP機能グループでは`文字列を整数に変換する`と`文字列を小数に変換する`の入力文法を変更しませんでした。
後者を指数対応する別契約はDTXT機能グループで完成し、現在は`「1e2」`を正確な`100.0`として受理します。
`文字列を整数に変換する`は引き続き指数を拒否します。現行の入力文法、診断、適合データは
[DTXT機能グループ仕様](decimal-text.md)を参照してください。

## 7. JSONとの境界

BSBソースとJSONは指数表記を別々に走査します。`JSONを解析する`はJSON機能グループのRFC 8259文法、
`E_JSON_SYNTAX`、`E_JSON_NUMBER_LIMIT`を維持します。フロントエンドから`jp.bsb.json`へ依存したり、
JSONの入力位置・reasonをBSB数値診断へ流用したりしません。

共有してよいのは、ASCII小数字句から丸めなしの係数、有限幅指数、数字数、構築前・正規化後の
精度とスケールを測る内部ユーティリティです。共有しても公開診断と文法の呼出し側契約は分離します。

## 8. 互換性と非変更点

- 既存の整数・固定小数点リテラルの型、値、表示、`format`結果は変わらない
- `1e3`を不正とした旧適合期待はEXP機能グループで置き換える
- DTXT機能グループ以降、`文字列を小数に変換する`は独立した実行時契約で指数を受理する
- `check --json`と`explain --json`の`schemaVersion=1`、必須メンバー、終了コードは変えない
- 組み込み語を追加しないため、公開辞書は107語のまま
- JSONリテラル、初等関数、暗黙変換、桁区切り、全角数字は追加しない
