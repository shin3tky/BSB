# HTTPS機能グループ: 最小HTTPS

> 本文は現行実装の規範契約です。
>
> ここで明示する追加以外は、先行する実装済み機能グループの契約を維持します。
> [診断と失敗境界](https-diagnostics.md)および[適合性](https-conformance.md)と一体です。
> 後続の有限再試行は[HTTP信頼性](http-reliability.md)が本仕様の`retryPolicy=none`境界を
> 拡張します。値、語、最終返値の契約は本仕様を維持します。

## 1. 目的と機能境界

HTTPS機能グループは、論理接続、`JSON`、`結果<T,E>`、不変`バイト列`を1本の同期HTTPS呼出しへ接続します。
同じBSB参照プログラムを、実ネットワークを使わない偽HTTP能力と、JDKのHTTPS実装を使う埋込み実環境の
両方で終端まで実行できることを優先します。

HTTPの意味論は[RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html)、URIの構成は
[RFC 3986](https://www.rfc-editor.org/rfc/rfc3986.html)を基準にします。HTTPクライアント固有の型、
絶対URI、資格情報、TLS設定をBSB値へ公開しません。

最小HTTPS機能グループ単独では次を追加しません。

- 自動リダイレクト、自動再試行、`Retry-After`、レート制限、冪等性キー
- OAuth 2.0、Basic認証、Cookie jar、プロキシ、相互TLS、利用者指定trust store
- 圧縮・自動展開、ストリーミング、並行・非同期送信、接続プールの公開契約
- multipart、form encoding、ファイル本文、trailers、WebSocket、HTTP/3
- 任意URL、動的論理接続名、動的HTTPメソッド、要求単位のtimeout・size上書き
- HTTP状態コードを失敗値へ変える語、JSON応答の自動判定・自動解析
- 標準CLIへ接続設定や秘密を渡す新しい引数、解決済み接続計画の公開CLI

## 2. 公開値

### 2.1 `HTTP要求`

`HTTP要求`は、相対経路、順序付き問い合わせ項目、要求ヘッダー、本文の有無を保持する、null非許容・
不変・利用者構築可能な不透明値です。空要求から始め、各設定語は元値を変更せず新しい要求値を返します。
論理接続名、HTTPメソッド、基底URI、timeout、size方針、資格情報を値に保持しません。これらは送信語の
静的引数と、送信時に再解決するホスト方針だけから決まります。

要求本文は「不在」と「長さ0の本文」を区別します。JSON・文字列本文は設定時にUTF-8バイト列へ固定し、
バイト列本文は既存の不変ストレージを共有できます。本文設定は`Content-Type`、`Accept`、
`Content-Length`を暗黙追加しません。利用者が必要な表現メタデータをヘッダー設定語で明示します。

要求値は保存、合流、利用者定義語、`任意`・`結果`の型引数に使えます。表示、等値比較、配列要素には
使えません。

### 2.2 `HTTP応答`

`HTTP応答`は、最終状態コード、大小文字を区別しない名前ごとの応答ヘッダー値一覧、完全に受信した
本文`バイト列`を保持する、
null非許容・不変・利用者構築不能な不透明値です。1xxの中間応答、HTTP版、理由句、接続先、TLS情報、
経過時間、接続再利用情報、trailersは保持・公開しません。

状態コードは200〜599の整数です。1xxは中間応答として消費し、101によるprotocol切替はHTTPS機能グループでは
`protocolFailure`です。3xxはリダイレクトせず、4xx・5xxを含む全最終応答を通信成功として
`HTTP応答`へ入れます。204、304、HEAD応答等で本文がない場合も、本文取出しは空`バイト列`を返します。

応答値は保存、合流、利用者定義語、`任意`・`結果`の型引数に使えます。表示、等値比較、配列要素には
使えません。

### 2.3 `HTTP送信失敗`

`HTTP送信失敗`は、通信操作が応答完成前に回復可能に失敗したことを表す、null非許容・不変・
利用者構築不能な閉じた型です。保持する公開情報は次の安定ASCII種類1個だけです。

| 種類 | 意味 |
|---|---|
| `nameResolutionFailure` | 対象ホストの名前解決に失敗した |
| `connectTimeout` | 接続確立が接続timeoutを超えた |
| `connectionFailure` | 名前解決・TLS以外の接続確立または接続維持に失敗した |
| `tlsFailure` | TLS handshake、証明書、ホスト名検証に失敗した |
| `responseTimeout` | 送信開始後、完全な最終応答の受信が応答timeoutを超えた |
| `responseTooLarge` | 応答本文が接続方針の上限を超えた |
| `responseHeadersTooLarge` | 応答ヘッダーの個数または総量が第6節の上限を超えた |
| `protocolFailure` | HTTPメッセージまたは応答メタデータが本仕様の契約を満たさない |
| `transportFailure` | 上記へ安全に分類できない回復可能な通信失敗 |

種類から「再試行可能」を導出しません。送信済みバイト数、HTTPメソッド、URI、ホスト名、例外、
証明書、応答接頭辞、自由文は保持しません。表示、等値比較、配列要素には使えません。

## 3. 静的送信引数

送信は次の構文で、論理接続名とHTTPメソッドを静的に指定します。

```text
HTTP要求を送信する<顧客管理API,POST>
```

```text
httpSendArguments := "HTTP要求を送信する" "<" identifier "," httpMethod ">"
httpMethod        := "GET" | "HEAD" | "POST" | "PUT" | "PATCH" | "DELETE"
```

`<`は正規語の直後へ空白なしで置きます。引数内の通常の区切りは許しますがコメントは許しません。
フォーマッタの正規形は空白なしの`<顧客管理API,POST>`です。接続名はCONN機能グループの宣言へ静的解決し、
メソッドは大文字ASCIIの6値だけを受理します。文字列、変数、型名、計算結果はどちらの引数にも使えません。

CONN機能グループの`論理接続を確認する<名前>`の構文と意味は変更しません。送信前の確認は必須ではなく、確認済み
結果をキャッシュしません。送信語は到達するたびに接続を再解決します。

既存136語の後ろへ次の13語を表の順で追加し、辞書は149語になります。別名はありません。

| `HTTP要求にヘッダーを設定する` | なし | `HTTP要求 文字列 文字列 -- HTTP要求` | なし | 同名を置換する |

通常帰還します。ただし捕捉不能診断と内部失敗では実行を終了します。

`HTTP要求に本文がある`は要求を残す判定語です。本文設定3語は既存本文を置換します。本文を不在へ戻す語は
HTTPS機能グループでは追加しません。

## 5. 経路、問い合わせ、対象URI

### 5.1 相対経路

経路入力はUnicodeスカラー値列です。空文字列、または`/`で区切った相対セグメント列を受理します。
先頭`/`、`?`、`#`、U+0000、完全セグメント`.`・`..`は拒否します。既にpercent encodeされた入力を
受け取るモードはなく、`%`は通常データとして`%25`へ符号化します。

各セグメントをUTF-8化し、RFC 3986のunreserved
`ALPHA / DIGIT / "-" / "." / "_" / "~"`だけをそのまま残し、他の各バイトを大文字16進の
`%HH`へ符号化します。区切り`/`だけは区切りとして保持します。Unicode正規化、slash統合、末尾slash削除、
percent decode、dot-segment除去は行いません。

解決済み基底URIの末尾`/`へ符号化済み相対経路を連結します。RFC 3986の汎用relative resolutionで
authorityや基底pathを置換しません。結果のscheme、host、portは必ず基底URIと同じで、許可originも再確認します。

### 5.2 問い合わせ

問い合わせ項目は名前、値ともUnicodeスカラー値列で、空文字列も受理します。追加順と重複を保持します。
各名前・値を経路セグメントと同じUTF-8 percent encodingで符号化し、`name=value`を`&`で連結します。
空配列ならquery自体を付けません。`application/x-www-form-urlencoded`の`+`置換は行いません。

### 5.3 URI上限

生経路はUTF-8で8,192バイト以下、問い合わせは256項目以下です。percent encoding後のqueryは
65,536 ASCIIバイト以下です。基底URI、連結済みpath、`?`、queryを含む最終絶対URIは
65,536 ASCIIバイト以下です。候補全体を作る前に有限幅で長さを計算します。

## 6. ヘッダー

要求ヘッダー名はRFC 9110の`field-name = token`に一致する1〜256文字のASCIIです。比較時は
ASCII小文字化します。値はSP、HTAB、VCHARだけからなる0〜8,192 ASCIIバイトです。CR、LF、NUL、
その他の制御文字、非ASCIIを拒否します。

要求ヘッダーは最大128個、正規化名長・値長・区切りの合計は65,536バイト以下です。同名設定は元の位置で
値1個へ置換し、大小文字違いの重複を作りません。次の接続・framing・認証用ヘッダーは利用者設定を
拒否し、実HTTP能力だけが必要に応じて生成します。

```text
authorization
connection
content-length
expect
host
proxy-authorization
te
trailer
transfer-encoding
upgrade
```

APIキー認証のヘッダー名が利用者設定と衝突する場合、送信直前にホスト認証値が同名値を置換します。
ヘッダー名や秘密値をBSBへ返しません。`Content-Type`、`Accept`、`User-Agent`は利用者が設定できます。
実装が独自`User-Agent`を暗黙追加しても、偽能力へ渡す論理要求と適合観測には含めません。

応答は最大128 field value、正規化名・値・区切りの合計65,536バイト以下です。応答名はtoken、値は
SP、HTAB、VCHARだけを受理し、先頭・末尾OWSを除きます。HTTP/2 pseudo-header、接続固有メタデータ、
trailersは公開ヘッダーに含めません。名前検索はASCII大小文字を区別せず、同名値の受信順を保持します。
異なる名前間の順序は公開せず、カンマ結合も行いません。

## 7. 本文

JSON本文は既存の規範JSON直列化を使い、そのUTF-8バイトを本文にします。整形、末尾改行、BOM、
文字コード指定を加えません。JSON構築・作業予算とバイト列構築・作業予算を既存規則どおり消費します。

文字列本文はBYTES機能グループのBOMなし・正規化なしUTF-8符号化と同じです。バイト列本文は内容を変更しません。
いずれも要求方針の本文上限67,108,864バイト以下でなければ送信しません。本文不在のGET・HEADだけを
HTTPS機能グループで許し、GET・HEADに長さ0を含む本文がある場合は捕捉不能診断です。POST、PUT、PATCH、DELETEは
本文不在と本文ありの両方を許します。

応答本文はContent-Type、Content-Encoding、状態コードにかかわらず、転送符号をHTTP層で除いた
content octet列として不変`バイト列`へ入れます。自動展開、文字コード変換、BOM除去、JSON解析をしません。
利用者はContent-Typeを検査し、本文を明示的にUTF-8復号してから`JSONを解析して結果を返す`へ渡します。

## 8. 接続解決と認証

送信はCONN機能グループの`connection.resolve`を呼出し時に1回だけ使います。`RESOLVED`方針をCONN機能グループの順で
再検証し、静的メソッドが許可メソッド集合にあること、対象URIが基底originかつ許可originであることを
検査します。`redirectPolicy=deny`を受理します。再試行方針はHTTP-REL機能グループの`none|bounded`を受理し、
要求単位の上書きはありません。

HTTPS機能グループの実送信が対応する認証方式は`none`と`apiKey`です。`basic`と`oauth2`はCONN機能グループでは妥当な
分類のままですが、HTTPS機能グループの送信では捕捉不能な未対応診断にします。

`apiKey`では、`http.send`能力を所有する埋込みホストが不透明`CredentialReference`を、次の秘密値へ
対応させます。

- RFC 9110 tokenに一致し、前節の予約名でないヘッダー名
- 1〜8,192 ASCIIバイトで、SP・HTAB・VCHARだけからなるヘッダー値

資格情報の未設定、利用拒否、不正は通信失敗値にせず、能力・設定境界の捕捉不能診断にします。
認証値は最終対象と方針検査後、送信直前に1回だけ適用します。リダイレクトがないため別originへ転送されません。

## 9. HTTP能力と実通信

実行環境は任意で`http.send`能力を1個提供できます。能力は、検証済みの次だけを受け取ります。

- 正規化済み論理接続名と静的HTTPメソッド
- 絶対対象URIを外部公開しない内部対象
- 利用者ヘッダーの不変コピー
- 本文の有無と不変バイト列
- 検証済み接続方針と不透明資格情報参照
- その呼出しで許される応答本文バイト上限

能力応答は、完全な`RESPONSE`、第2.3節の`FAILURE`、`CANCELLED`、認証の
`CREDENTIAL_NOT_CONFIGURED`・`CREDENTIAL_DENIED`・`CREDENTIAL_INVALID`の閉じた状態です。
自由文、例外、部分応答を返しません。未知状態、null、名前・method不一致、上限を超える成功応答などは
内部エラー70です。能力自体の契約失敗は既存`E_CAPABILITY_FAILURE`です。

標準実装はJDK 25の同期`java.net.http.HttpClient`を使います。JDK実装には接続失敗の自動再試行を制御する
process-wide propertyがあるため、
[JDK 25の`java.net.http` module契約](https://docs.oracle.com/en/java/javase/25/docs/api/java.net.http/module-summary.html)
に従い、最初のclient作成前に次の安全preflightを通らなければ`JdkHttpsTransport`を構築しません。

- `jdk.httpclient.disableRetryConnect`が文字列`true`
- `jdk.httpclient.enableAllMethodRetry`が未設定または文字列`false`
- `jdk.internal.httpclient.disableHostnameVerification`が未設定または文字列`false`
- `jdk.httpclient.HttpClient.log`が未設定または空。JDKのheader・content loggingを通常実行で許可しない

propertyをライブラリ内から変更しません。埋込みホストまたは起動コマンドがclient初期化前に設定し、
transport構築時に検証します。契約外なら秘密やproperty値を含まないホスト構成失敗です。その上で次を強制します。

- URI schemeは`https`だけ。証明書とホスト名を既定PKIX規則で検証し、検証無効化APIを公開しない
- `Redirect.NEVER`、明示的な無proxy selector、自動再試行なし、同期1要求
- TLS 1.2または1.3だけを許可する。既定trust storeとendpoint identificationを使う
- 接続timeoutは接続方針、応答timeoutは送信開始から最終応答本文完了までの全体期限
- 応答本文はストリームから上限+1バイトまで読み、超過時は閉じて完全応答を作らない
- `Content-Length`が本文上限を超えると判明した場合は本文を読まず`responseTooLarge`
- `Accept-Encoding`を暗黙追加せず、content encodingを自動展開しない
- HTTP/1.1またはHTTP/2を利用できるが、版や接続再利用を公開意味論にしない

HTTP待機区間は既存30秒の能動実行時間から除外し、接続・応答timeoutで必ず制限します。利用者が実行全体を
取り消した場合は結果失敗ではなく`E_HTTP_CANCELLED`です。

## 10. 能力と静的説明

送信1呼出しは平坦な`connection.resolve`と`http.send`の能力・副作用を持ちます。
`parameterizedCapabilities`の外側・内側`schemaVersion=1`を維持し、同じ論理接続へ操作`resolve`と
静的HTTPメソッドを追加します。

操作の規範順は次です。

```text
resolve, GET, HEAD, POST, PUT, PATCH, DELETE
```

同じ利用者語内・推移要求内の重複は接続名と操作ごとに統合します。接続宣言の`uses`では、送信呼出し位置を
HTTPメソッドの操作として1件掲載します。送信が暗黙に行う再解決は同じ位置の`resolve`要求としても掲載します。
静的に到達不能な送信は既存規則どおり要求へ含めません。

静的説明には要求の経路、query、ヘッダー、本文、基底URI、解決成否、認証方式、資格情報、timeout、sizeを
含めません。値から実行時の設定内容を推論しません。解決済み計画CLIは対象外です。

## 11. 資源

| 資源 | 上限 | 単位 |
|---|---:|---|
| 1要求の生経路 | 8,192 | UTF-8バイト |
| 1要求のquery | 256項目、65,536 | percent encode後ASCIIバイト |
| 1要求のheader | 128値、65,536 | 正規化名・値・区切りバイト |
| 1応答のheader | 128値、65,536 | 正規化名・値・区切りバイト |
| 1対象URI | 65,536 | ASCIIバイト |
| 1実行のHTTP送信 | 1,024 | 送信語を受理した回数 |
| 1実行の要求本文試行 | 134,217,728 | 本文バイト |
| 1実行の応答本文受信 | 134,217,728 | 実際に読んだ本文バイト |
| 1実行のHTTPメタデータ構築 | 16,777,216 | 経路・query・headerの新規論理バイト |

要求本文試行は、resolverへ委譲する前に本文長を全量加算します。接続未設定等で実送信しなくても戻しません。
応答本文受信は、成功では本文長、chunked等の接続方針超過では上限を越えた最初の1バイトまでを加算します。
HTTP総受信残量が接続方針より小さい場合は残量を能力上限とし、越える直前までを累積へ加えて
`E_HTTP_RESPONSE_TOTAL_LIMIT`にします。越えた1バイトで累積値を上限より大きくしません。

`Content-Length`だけで接続方針超過が確定した場合は、本文を読まず`responseTooLarge`、受信加算0です。
長さが接続方針以内でもHTTP総受信残量を超えると確定した場合は、本文を読まず
`E_HTTP_RESPONSE_TOTAL_LIMIT`、受信加算0です。両上限を同時に超える場合は接続方針を先に分類します。

HTTP metadata構築は、経路設定なら符号化済みpath長、query追加なら追加する符号化済み`name=value`と
必要な`&`、header設定なら正規化名・値・`": "`・改行相当の新しいfield長を加算します。置換前の値や、
不変共有する既存metadata全体を再加算しません。本文設定と応答header受信はこの予算へ数えません。

完全応答から`バイト列`を構築する時は、既存バイト列1値64 MiB・構築128 MiBを重ねて適用します。
HTTP本文予算を消費したことを理由にバイト列予算を省略しません。ヘッダー値一覧の取出しは既存配列構築予算を
消費します。

## 12. 実行順序と原子性

送信語は次の順で判定します。

1. 既存の命令数と能動実行時間
2. 静的引数と入力要求値の内部不変条件
3. `connection.resolve`と`http.send`能力の存在
4. HTTP送信回数、要求本文試行の累積上限
5. 接続解決を1回実行し、状態と方針を再検証
6. method許可、GET・HEAD本文禁止、要求メタデータ、対象URI、要求本文方針上限
7. 認証方式対応と資格情報境界
8. HTTP待機除外を開始し、`http.send`を1回実行し、必ず待機除外を終了
9. 能力契約、取消、資格情報状態、通信失敗を分類
10. 応答header、status、本文長、HTTP受信累積を検査
11. バイト列構築予算と結果を積むデータスタック上限を検査
12. 入力要求を成功または失敗結果へ1回で置換

回復可能な通信失敗は正常な1対1置換で、runの終了は後続プログラムに従います。4xx・5xxも成功結果です。
捕捉不能診断では要求入力、保存値、stdout、プログラムstderrを変更しません。能力へ委譲済みなら物理送信、
受信済みバイト、能力イベント、要求試行・応答受信予算は戻しません。拒否された予算予約は累積値を変更しません。

要求設定語は入力全体、候補長、予算、スタック上限を検査してから、入力要求と引数を新要求1個へ置換します。
診断時は入力スタックと元要求を不変にします。

## 13. 非開示とトレース

`HTTP要求`、`HTTP応答`、`HTTP送信失敗`は通常trace、診断`dataStack`、安全表現で常に次のように伏せます。

```text
HTTP要求:<redacted>
HTTP応答:<redacted>
HTTP送信失敗:<redacted>
```

入れ子の`任意`・`結果`も状態ごと推移的に伏せます。経路、query、要求・応答header、本文、本文長、状態コード、
失敗種類を不透明値のtraceへ含めません。専用取出し語で得た状態コード、header文字列、失敗種類は通常値です。

能力イベントは能力名、既定で論理接続名、method、次の閉じた結果だけを保持します。

```text
response | failure | cancelled | credentialNotConfigured | credentialDenied |
credentialInvalid | capabilityFailure
```

`response`へ状態コードを、`failure`へ失敗種類を付けてもよいですが、URI、経路、query、header名・値、本文、
サイズ、timeout値、資格情報参照、秘密、例外を含めません。CONN機能グループの強い方針は接続名も伏せます。

資格情報の値は、BSB値、結果、診断全メンバー、両出力、通常trace、能力イベント、説明JSON、Java例外の
公開文面、参照アプリの通常ログへ一度も移しません。適合試験は各面に別の検出用秘密を置いて0件を要求します。

## 14. 偽環境と実環境

適合試験は実DNS、実時計待ち、実TLS、実ネットワークを使いません。偽`connection.resolve`と
偽`http.send`が、検証済み論理要求、完全応答、全失敗種類、資格情報状態、取消、timeout経過、本文上限、
能力例外を決定的に再現します。期待値をJDK HTTP実装の出力から生成しません。

実環境は同じ能力契約を実装する`JdkHttpsTransport`と埋込み例を提供します。標準CLIは接続設定を暗黙に読みません。
参照埋込みはホスト側だけで基底URI、許可方針、APIキーヘッダー名・値を受け取り、同じBSBソースを実行します。
実ネットワークのsmoke testは明示的な環境変数と利用者操作を必要とする任意試験とし、中央適合・通常ビルド・
配布合否には含めません。

## 15. 完了条件

- 同じ参照BSBが偽能力と実JDK HTTPS能力で、要求構築から応答JSON処理まで終端する
- 接続名とmethodが静的に説明され、送信時に再解決・再認可される
- path、query、header、3本文種別が不変要求値で構成でき、スタック深さを累積させない
- 3xx・4xx・5xxと通信失敗、取消、能力・設定診断が混同されない
- timeout、redirect deny、retry none、要求・応答・累積上限が偽能力でも決定的に検証される
- APIキーが送信時だけ適用され、全公開面から秘密が非開示になる
- 応答status、header、本文を個別に取り出し、本文を明示的にUTF-8・JSONへ進められる
- 全適合ID、中央カタログ、利用者サンプル、埋込み例、公開CLI配布回帰が過不足なく成功する
