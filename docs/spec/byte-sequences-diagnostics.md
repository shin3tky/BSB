# BYTES機能グループ: `バイト列`変換の診断と失敗境界

> 本文は現行実装の規範契約です。
>
> [不変バイト列仕様](byte-sequences.md)と[適合性](byte-sequences-conformance.md)に従います。

## 1. 新規診断

BYTES機能グループでは、回復不能な資源・範囲条件に次の4コードを追加します。すべて実行時、重要度error、
終了コード10です。UTF-8・Base64の入力データ不正は診断ではなく閉じた失敗値です。

| コード | 条件 | 必須fields |
|---|---|---|
| `E_BYTE_SEQUENCE_RANGE_OUT_OF_BOUNDS` | 一部取得が`0 <= start <= end <= length`を満たさない | `word`、`unit=byte`、`start`、`end`、`length`、`validRange` |
| `E_BYTE_SEQUENCE_SIZE_LIMIT` | 新しい1値が67,108,864バイトを超える | `word`、`operation`、`limitName=byteSequenceBytes`、`limit`、`observed` |
| `E_BYTE_SEQUENCE_CONSTRUCTION_LIMIT` | 累積構築が134,217,728を超える | `word`、`operation`、`limitName=byteSequenceConstructionBytes`、`limit`、`used`、`requested`、`observed` |
| `E_BYTE_SEQUENCE_WORK_LIMIT` | 累積作業が268,435,456を超える | `word`、`operation`、`limitName=byteSequenceWorkBytes`、`limit`、`used`、`requested`、`observed` |

`expected`と`actual`は表の数値・範囲から決定的に作り、`fixes`は入力範囲、本文サイズ、1実行の変換回数を
減らす候補を各1件だけ返します。上限判定に必要な`limit`、`used`、`requested`、`observed`、範囲値以外に、
バイト内容、Base64入力、復号接頭辞、ハッシュ等の派生情報を
文面・fields・expected・actual・fix・relatedへ含めません。

文字列結果が16,777,216 UTF-8バイトを超えるUTF-8復号・Base64符号化は既存
`E_STRING_UTF8_LIMIT`です。この2経路の同診断は`word`、`limit`、`observed`だけで判定でき、
入力バイト列のpreview、長さ以外の内容、復号済み接頭辞を追加しません。入力不足・型不一致・表示不能・
等値比較不能・配列要素禁止は既存
`E_STACK_UNDERFLOW`、`E_TYPE_MISMATCH`、`E_ARRAY_ELEMENT_TYPE_NOT_ALLOWED`を再利用します。

## 2. 回復可能な失敗

次だけを結果失敗へ変換します。

| 操作 | 結果失敗型 | 公開内容 | 診断 |
|---|---|---|---|
| UTF-8復号 | `UTF8復号失敗` | 6種類の安定ASCII値、最初の不正バイト位置 | なし |
| Base64復号 | `Base64復号失敗` | 4種類の安定ASCII値、最初の文字位置またはEOF | なし |

失敗結果を返して後続も正常終了したrunは終了0、CLI診断なしです。入力文字列・バイト列を失敗値に保持せず、
診断カタログへ種類ごとのコードを追加しません。

## 3. 捕捉不能境界

次は結果値へ変換しません。

| 条件 | 診断または終了 | 理由 |
|---|---|---|
| 1バイト列のサイズ超過 | `E_BYTE_SEQUENCE_SIZE_LIMIT` | 値上限 |
| 累積構築・作業超過 | 新規2資源診断 | 全実行の資源境界 |
| 文字列結果上限 | `E_STRING_UTF8_LIMIT` | 値上限 |
| 一部取得範囲外 | `E_BYTE_SEQUENCE_RANGE_OUT_OF_BOUNDS` | プログラム値の契約違反 |
| 型、スタック、合流、保存の誤り | 既存静的診断 | プログラム契約違反 |
| データスタック、命令数、実行時間上限 | 既存診断 | 全実行の制御・資源境界 |
| 能力不在・拒否、全実行取消 | 既存または後続診断 | ホスト境界 |
| null、可変配列露出、範囲不変条件違反 | 内部失敗70 | 処理系契約違反 |

復号中に資源上限へ達した状態を`UTF8復号失敗`や`Base64復号失敗`に見せかけません。将来HTTPが
`バイト列`を生成しても、応答サイズ、能力、取消、タイムアウトはHTTP側の契約に従い、復号失敗型へ
縮退させません。

## 4. 静的検査

新11語は固定スタック効果です。既存の静的検査、到達不能抑止、名前予約規則を適用します。

- 入力不足は`E_STACK_UNDERFLOW`
- 入力型違いは`E_TYPE_MISMATCH`
- `バイト列`、失敗2型、新11語の再定義は`E_RESERVED_NAME`
- `バイト列`または失敗型を含む値の表示は`E_TYPE_MISMATCH`、`expectedType=表示可能`
- 失敗型を含む値の等値比較は`E_TYPE_MISMATCH`、`expectedType=等値比較可能`
- `バイト列`自体の同型比較は有効
- 3新型の配列要素化は`E_ARRAY_ELEMENT_TYPE_NOT_ALLOWED`

表示・比較不能の原因型を決める既存走査は、`バイト列`と失敗2型を閉じた型特性として扱います。
`結果<バイト列,UTF8復号失敗>`のように複数原因がある場合も、正規型の左から深さ優先という既存の
決定順を維持し、Java列挙順やハッシュ順に依存しません。

## 5. 操作別の判定順

全操作は、既存の静的検査後、実行時に命令数・能動時間を検査してから次へ進みます。

### 長さ・一部取得

1. 入力値の内部不変条件
2. 一部取得だけ開始・終了範囲
3. 作業1の予約
4. スタック置換

範囲不正では作業を予約しません。一部取得は結果長が1値上限を超えないため、サイズ診断を重ねません。

### UTF-8符号化

1. 文字列の既存不変条件とUTF-8長を有限幅で計測
2. 1値バイト列上限
3. 同量の構築・作業を原子的に予約
4. 最短UTF-8を構築しスタック置換

現行文字列上限により通常は1値上限以下ですが、埋込み不正値に依存せず順序を維持します。

### UTF-8復号

1. バイト列の内部不変条件と1値上限
2. 入力長の作業を予約
3. 左から厳密UTF-8を検査
4. 不正なら失敗値へ置換
5. 有効なら結果文字列UTF-8長の既存上限を検査
6. 完成文字列を構築し成功結果へ置換

手順5で失敗した場合、入力走査作業は消費済みですが入力バイト列はスタックに残ります。

### Base64符号化

1. バイト列の内部不変条件と1値上限
2. `4 * ceil(N / 3)`をoverflowしない有限幅で計算
3. 結果文字列上限
4. 入力長と出力長の和を作業予約
5. 規範文字列を構築しスタック置換

### Base64復号

1. 入力文字列の既存不変条件とUTF-8長
2. 入力UTF-8長の作業を予約
3. `invalidCharacter`、`invalidLength`、`invalidPadding`、`nonZeroPadBits`の順で検査
4. 不正なら失敗値へ置換
5. 有効なら復号結果長を有限幅で計算し1値上限を検査
6. 結果長と同量の構築・追加作業を原子的に予約
7. 復号結果を構築し成功結果へ置換

手順3の失敗は入力走査作業を消費し、構築0です。手順5・6の診断では入力文字列を残し、先行作業を
戻しません。手順6の構築または作業どちらか一方だけを加算してはなりません。

### 等価比較

既存のラッパー状態と型一致を検査後、バイト列へ到達した時だけ処理します。長さ不一致は追加作業0です。
同長なら各位置の比較直前に作業1を予約し、最初の不一致で停止します。同一実体でも全位置を検査した
場合と同量を課金します。作業拒否では比較入力2値を残します。

## 6. 予算消費

| 終了 | 構築 | 作業 | スタック |
|---|---:|---:|---|
| UTF-8符号化成功 | 出力長 | 出力長 | `文字列`を`バイト列`へ置換 |
| UTF-8入力不正 | 0 | 入力長 | `バイト列`を失敗結果へ置換 |
| UTF-8復号成功 | 0 | 入力長 | `バイト列`を成功結果へ置換 |
| Base64符号化成功 | 0 | 入力長+出力長 | `バイト列`を`文字列`へ置換 |
| Base64入力不正 | 0 | 入力UTF-8長 | `文字列`を失敗結果へ置換 |
| Base64復号成功 | 結果長 | 入力UTF-8長+結果長 | `文字列`を成功結果へ置換 |
| 入力走査予約拒否 | 0追加 | 0追加 | 不変 |
| 走査後の結果予約拒否 | 0追加 | 入力分を維持 | 不変 |

空値の符号化・復号は要求量0を受理し、予算を増やしません。呼出し命令自体は既存命令予算へ常に1命令
として数えます。失敗値・結果ラッパーはバイト列構築へ数えません。

## 7. 原子性と非開示

回復可能な入力不正は正常な1対1置換です。失敗値、成功値とも全検査前にスタックへ公開せず、保存値、
stdout、プログラムstderr、能力イベントを変更しません。

捕捉不能診断では入力スタックを保ちます。共通`dataStack`はバイト列、失敗値、それらを含む任意・結果を
内容・長さ・状態ごと伏せます。Base64入力と変換後文字列も既存の文字列非開示規則を弱めません。
人間向けメッセージ、fields、expected、actual、fixes、relatedへ元値、16進プレビュー、Base64接頭辞、
UTF-8復号接頭辞、Java例外名を載せません。

内部値のnull、長さとストレージ範囲の不一致、外部変異の検出、未知の失敗種類は、利用者入力不正へ
推測変換せず内部失敗70です。`OutOfMemoryError`や`StackOverflowError`を規範診断として認めません。

## 8. 実装監査点

- バイト列実体が入力配列を防御コピーし、内部配列や可変viewを返さない
- sliceが共有実装でも元・結果の論理内容を変更できない
- UTF-8検証がソース入力用BOM除去やJavaの置換デコーダを再利用しない
- Base64復号がMIME・URL-safe・無padding・非0 pad bitを寛容に受理しない
- 回復可能失敗の値が原入力または例外を保持しない
- 構築・作業の同時予約で片側だけを加算しない
- 結果長計算が`int`乗算overflowや巨大な一時配列に依存しない
- バイト列を含むラッパーの表示・比較・trace特性を全型引数から反復的に導く
- trace有無が結果、課金、診断、スタック、能力イベントを変えない
- 後続HTTPが同じ値・上限・非開示・予算APIを再利用できるが、HTTP固有失敗を本機能グループへ混ぜない
