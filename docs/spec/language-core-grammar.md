# CORE機能グループ: 字句・構文・名前境界

> 本文は現行実装の規範契約です。

## 1. 処理順序

ソースは次の順序で処理します。

```text
元バイト列
  → ソースサイズ検査
  → UTF-8検証と先頭BOM除去
  → 字句解析
  → 構文解析
  → 定義名収集
  → 名前解決
  → 型・スタック効果検査
  → IR生成
```

前の段階にエラーがある場合は後続機能グループへ進みません。警告は処理を止めません。

UTF-8デコーダは不正な入力をU+FFFDへ置換せず、最初の不正バイト位置から `E_INVALID_UTF8` を報告します。

## 2. BOM

元バイト列の先頭3バイトが `EF BB BF` の場合、その1個だけをBOMとして取り除きます。2個目以降の同じ列はU+FEFFとして字句解析され、`E_INVISIBLE_CHARACTER` です。BOMだけのファイルは空ソースと同じ構文ですが、`check` と `run` では `E_MISSING_MAIN` です。

人間向けの最初のトークン位置は1行1列です。UTF-8バイト位置は元バイト列を基準にするため、BOMつきの最初のトークンは `utf8Start = 3` です。

## 3. トークンと区切り

CORE機能グループのトークン種別は次のとおりです。

```text
IDENTIFIER
INTEGER_LITERAL
DECIMAL_LITERAL
BOOLEAN_LITERAL
CHARACTER_LITERAL
STRING_LITERAL
PARTICLE
RESERVED_SYNTAX
STACK_OPEN_FULLWIDTH
STACK_CLOSE_FULLWIDTH
STACK_OPEN_ASCII
STACK_CLOSE_ASCII
STACK_SEPARATOR
DEFINITION_END
COMMENT
```

U+0020、U+0009、U+3000、LF、CR、CRLF、`、`、`，` はトークンを区切ります。コメントは位置と本文を保持しますが、実行トークンではありません。BOM、区切り、コメント、EOFはトークン数上限へ数えません。

`。` は `DEFINITION_END` です。ASCIIの `,`、`.`、`?`、全角の `？` など、どのトークンにも属さない文字は `E_UNEXPECTED_CHARACTER` です。

## 4. 識別子の走査

識別子候補は、区切り、`。`、`#`、括弧、ASCII引用符の直前までを1候補として読みます。候補の途中に `-`、`?` など識別子へ使用できない文字がある場合、前後へ暗黙分割せず、候補全体へ `E_INVALID_IDENTIFIER` を報告します。

識別子候補へ、全角英数字の限定変換、NFC、Unicodeカテゴリー検査、不可視文字検査、128コードポイント上限の順に適用します。

助詞と予約語は、正規化後の識別子全体が予約名と一致した場合だけ分類します。部分一致では分類しません。たとえば `一行を入力する` に含まれる `を` は助詞トークンではありません。

## 5. 数値候補の走査

> 本節はCORE機能グループ完成時の規則です。EXP機能グループでは[指数表記仕様](exponent-literals.md)と
> [指数診断仕様](exponent-literals-diagnostics.md)が、指数を含む候補、有効接頭辞、失敗順を上書きします。

ASCII数字、またはASCII `-` の直後にASCII数字が続く位置から始まる候補は、次の区切りまで数値候補として読みます。数値として有効な接頭辞の直後に識別子文字が続く場合は `E_MISSING_SEPARATOR`、それ以外で候補全体が整数または小数の文法に一致しない場合は `E_INVALID_NUMBER_LITERAL` です。

このため、`123abc` と `-3個` は `E_MISSING_SEPARATOR`、`01`、`.5`、`1.`、`1e3` は `E_INVALID_NUMBER_LITERAL` であり、いずれも複数トークンへ分割しません。`.5` は `.` の位置から不正な数値候補として扱います。ASCII `-` 単独は `E_UNEXPECTED_CHARACTER` です。

### 5.1 引用リテラルの終端

文字列または文字の閉じ引用符は、そのリテラルトークンを確定します。閉じ引用符の直後には、区切りなしで助詞、識別子、`。`、コメントを続けられます。たとえば `「左」と「右」を 等しい` と `'A'を 表示する` は有効です。`format` はリテラルと直後の助詞または識別子の間へASCII空白を1個入れます。

## 6. 定義開始の分割

トップレベルで、区切りの直後またはファイル先頭から始まる識別子候補が、正確な文字列 `とは` で終わる場合、最後の `とは` を定義開始標識として分離します。残る接頭辞が空でなく、有効な識別子でなければなりません。

```text
メインとは       → 名前 `メイン` + 定義開始
意味とはとは     → 名前 `意味とは` + 定義開始
```

単語本体中ではこの分割を行わず、`意味とは` 全体を識別子として扱います。

トップレベルで `識別子`、区切り、予約語 `とは` の順に現れた場合は `E_DEFINITION_ADJACENCY` です。それ以外の、定義開始にならないトップレベルトークンは `E_UNEXPECTED_TOP_LEVEL` です。

## 7. 定義終端

単語本体中の正規化後の識別子全体が `こと` で、その直後に次のいずれかだけを挟んで `。` が続く場合、定義終端として扱います。

- 何も挟まない
- U+0020、U+0009、U+3000を1個以上挟む

改行、コメント、`、`、`，`を `こと` と `。` の間に置けません。その場合は `こと` を予約語として認識した位置へ `E_EXPECTED_DEFINITION_END_MARK` を報告します。フォーマッタの正規表記は `こと。` です。

文字列・文字・コメント内の `こと。` は終端ではありません。

## 8. 文法

`HSPACE` はU+0020、U+0009、U+3000、`SEPARATOR` はすべての空白、改行、`、`、`，`です。コメントは、トークン間へ現れ得る非実行要素です。

```text
source          := trivia* (wordDefinition trivia*)* EOF

wordDefinition  := definitionStart separator+ stackEffect
                   body
                   definitionEnd

definitionStart := identifier immediately-followed-by "とは"
definitionEnd   := "こと" HSPACE* "。"

stackEffect     := "（" effectSides "）"
                 | "(" effectSides ")"

effectSides     := typeList? separator* "--" separator* typeList?
typeList        := userType (separator+ userType)*
userType        := identifier

body            := (literal | bodyName | particle | trivia)*
bodyName        := identifier | nonterminatingReservedName
trivia          := separator | comment
```

開始括弧と終了括弧は同じ種類でなければなりません。型位置の識別子は構文解析後に分類します。`整数`、`真偽`、`文字`、`文字列` はCORE機能グループの型、予約済みの後続機能グループ型は `E_FEATURE_NOT_AVAILABLE`、`T` と `表示可能` は `E_TYPE_CONSTRAINT_NOT_ALLOWED`、それ以外は `E_UNKNOWN_TYPE` です。CORE機能グループに利用者定義型はありません。

コメントは定義開始とスタック効果の間、およびスタック効果の括弧内には置けません。該当する `#` へ `E_COMMENT_NOT_ALLOWED` を報告します。これにより、フォーマッタはコメントを別の構文トークンの後ろへ移動せずに定義ヘッダーを1行へ正規化できます。

`bodyName` は字句上で名前として分類されたトークンです。静的検査で、利用可能な組み込み単語または利用者定義単語なら呼び出し、後続機能グループの予約名なら `E_FEATURE_NOT_AVAILABLE`、型・型制約・現在の構文・`メイン`なら `E_NAME_NOT_CALLABLE`、それ以外なら `E_UNDEFINED_WORD` に分類します。`こと` は定義終端の判定を優先し、終端にならない配置では構文エラーです。

辞書専用の型制約 `T` と `表示可能` は `userType` ではありません。利用者のスタック効果に書いた場合は `E_TYPE_CONSTRAINT_NOT_ALLOWED` です。

CORE機能グループには入れ子構文がないため、構文入れ子の最大深さは自然に1以下です。D-037の256段上限はFLOW機能グループ以降の構文へ適用し、CORE機能グループでは到達不能です。

## 9. 予約名と機能グループ

### CORE機能グループで利用可能

| 分類 | 名前 |
|---|---|
| 特別な名前 | `メイン` |
| 型 | `整数`、`真偽`、`文字`、`文字列` |
| 値 | `はい`、`いいえ` |
| 助詞 | `を`、`に`、`と`、`から`、`で` |
| 構文 | `とは`、`こと` |
| 単語 | `足す`、`引く`、`掛ける`、`等しい`、`表示する`、`一行表示する`、`改行する` |

`は` は将来の宣言構文用に予約しますが、CORE機能グループの助詞としては利用できません。

型名、辞書専用の型制約、構文名を単語本体の呼び出し位置で使った場合は `E_NAME_NOT_CALLABLE` です。`メイン` も呼び出せません。実行処理だけがエントリポイントとして `メイン` を開始します。

## 10. `メイン`

空ソースとコメントだけのソースは構文として有効です。`format` は成功しますが、`check` と `run` は `E_MISSING_MAIN` です。

`メイン` はちょうど1回定義し、宣言を正確に `（--）` とします。2回目は `E_DUPLICATE_NAME`、異なる効果は `E_INVALID_MAIN_EFFECT` です。

`メイン` の効果が不正な場合、その本体の型・スタック検査を省略して派生診断を抑止し、他の単語の検査は続けます。

## 11. 診断回復

字句解析は、文字列や文字の閉じ忘れでは物理行末、その他の不正候補では次の区切りまでを1エラーとして回復します。構文解析は次の定義終端、または次の有効な定義開始までを回復単位とします。

同じ候補や欠落から派生する診断は1件にまとめます。診断の上限と順序は [language-core-diagnostics.md](language-core-diagnostics.md) に従います。
