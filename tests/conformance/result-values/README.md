## 機械形式

- `manifest.json`: 今回の限定ID・variant・コマンド、補助分析期待、全機械資源のSHA-256。
  manifest自身とREADMEだけはハッシュ対象外です。`languageImplemented`と`conformanceExecuted`は
  型・静的検査の範囲、`runtimeImplemented`と`runtimeConformanceExecuted`は実行時検証の範囲の
  実装・実行完了を表すtrueです。
- `cases.tsv`: [承認済み22列](../../../docs/spec/result-values-conformance.md)。`diagnostic_rows`は
  そのvariantの全コマンドに対する`diagnostics.tsv`行数の合計です。
- `diagnostics.tsv`: 承認済み16列。`fields`、`fixes`、`related`はコンパクトJSONです。
  `span`列は公開版1の`span`または`point`に、独立の`utf16Start`・`utf16EndExclusive`を加えます。
  公開CLIにはUTF-16補助メンバーを追加しません。空を表すJSONと未適用の`-`を区別します。
- `expected/*.stdout.json`・`*.stderr.json`: コマンド名から期待ストリームの文字列への写像。
  JSONとして1回decodeした文字列をUTF-8へ符号化し、CLI出力とバイト比較します。
  各CLI JSON本文も改行を含めて固定されており、部分一致やJSONメンバーの射影ではありません。
- `expected/*.state.json`: 実行できる正常例の最終状態。型・スタック等の分析用期待は
  manifestから参照する`*.analysis.json`です。静的失敗はrunコマンドを呼んでもInterpreterは
  実行されないため、最終状態と実行予算は`-`にします。
- `resources.tsv`: 承認済み8列。公開ソース・型モデル・値モデル・Lexerを`target`で区別します。
  `generated/*.properties`の`kind`が入力の再構築方法、`expected`が独立期待への参照です。
- `generated/resources.tsv`: `generator_key input_kind sha256 recipe_sha256`の4列。
  `input_kind=source`は生成するBSB本文、`recipe`は型モデルの正規レシピ自体をハッシュ化します。
  全行でレシピ本文のハッシュも固定し、モデル側の共有条件・ペイロード指定の変更を検出します。
- `central/catalog.tsv`: 全70 IDの証跡と公開／既存／内部境界を閉じる中央カタログです。
- `central/command-hashes.tsv`: 中央カタログの公開24ソース×5コマンドの終了値・両出力ハッシュ・バイト数です。
- `central/file-hashes.tsv`: 中央カタログの固定成果物34件のSHA-256とバイト数です。このカタログ自身は
  自己参照ハッシュにせず、厳格ローダーとデータ検査がヘッダー・行数・重複・全参照を検査します。
- `chapter/*`、`explain/*`: 章末stdout／状態／通常・非開示trace／explainとN13-017 explainの全体期待です。

公開CLIのソース引数はリポジトリルートからの
`tests/conformance/result-values/sources/<ID>-<variant>.bsb`です。診断のsourcePathもこの文字列です。
実行前後のsourceハッシュを比較します。formatの2回目だけは一時ファイルを使えます。
Rの大きなsourceはチェックインせず、レシピから生成したUTF-8本文をハッシュで確認して使います。
`--input`は標準出力へ返すだけでファイルを書きません。

## 期待値の由来と回復規約

期待は[結果値](../../../docs/spec/result-values.md)、[診断](../../../docs/spec/result-values-diagnostics.md)、
既存のformat／CLI／診断規約とメッセージ資源から作りました。作成ツールは処理系を起動せず、
固定したソース雛形、診断テンプレート、UTF-8／UTF-16の位置計算、有限の生成式だけを使います。
BSBソースを汎用に解析・実行する実装ではありません。

期待の具体化で、次の実装上の注意を明示しました。承認済みの診断優先順位を変えるものではありません。

- 空引数・区切り不足・個数不一致・終端不足の新規構文診断は挿入位置を`point`として記録します。
  EOF例も末尾LFを持ち、位置はその直後です。裸型・型名・予約名は名前全体の`span`です。
- 結果型の壊れた引数枠を原因とするEOF例は、結果値が規定する一次診断だけを期待します。
  現行Parserは外側のヘッダー／語終端不足を別途追加し得るため、結果型経路では派生抑止が必要です。
- 同一EOF位置で結果・任意の複数終端が欠落する場合、規範の「内側から」を期待します。
  現行`Diagnostic.ORDERING`のコード名順だけでは、外側任意・内側結果の順が逆転します。
  この混在ケースの順序保証は処理系実装時の確認点です。既存の結果を含まない診断順は維持します。
- 100件目の通常診断は`E_DIAGNOSTIC_LIMIT`へ置換する既存契約です。
  不正定義100／101個でも期待は通常99件＋上限通知1件、`observed=100`であり、101件を出しません。
  上限で停止した場合、後続`メイン`へ到達したとは期待しません。
- 幅広型は型引数を入出力に複製するとトークン上限が先に来ます。公開ソースは入力側1回だけの
  注釈と結果破棄を使い、163,851トークンに収めます。共有／非共有は別の型モデル入力です。
- 同じ型名の制約／未知型が左右両方にある場合も、それぞれの位置で診断します。
  現行の名前単位の重複抑止を、独立した結果型引数にそのまま流用しません。

共通診断の文面は既存資源に由来します。言語コア・数値演算と書かれた既存文面を勝手に
改訂していません。新しい型引数内コメントのexpectedは`型引数`、構築名と`<`の間なら
`型引数開始の<`として固定しました。結果を配列の要素型にする診断のfixは
`結果値を配列の外で個別に処理してください`です。

## 確認方法と現在の結果

```shell
python3 tools/result-values_data.py --check
python3 -m unittest discover -s tools -p 'test_result-values_data.py' -v
python3 tools/result-values_data.py --input RESULT-R001-success-256
git diff --check
```

`--check`は既存資源を再計算した独立期待と比較する読取り専用検査です。追加・欠落・差異を
報告し、自動更新しません。`--patch <ID>`はそのIDの編集候補をapply_patch形式で標準出力へ
返すだけです。通常の検証・実装作業で期待を自動上書きする用途には使いません。

18件のデータ検査が成功しました。構成、重複・不足・余剰拒否、ソース位置、コマンド出力との
対応、両型の受理集合、レシピ未使用項目拒否、33生成ハッシュ、トークン算術、型深さ、
値・ハッシュ関係、診断順と件数を確認しています。
実装後はN/F 136 variantsの671 CLI呼出しを終了値・stdout・stderr・入力不変・標準形まで比較し、
R 33 variantsを実際のfrontend・静的検査・型モデルへ通しました。runtime検証ではruntime／trace／CLI／
資源境界の新規20試験を加えました。中央カタログでは中央カタログ、公開CLI、章末、RESULT-R014の
新規5試験を追加し、結果値全対象試験とJaCoCoが成功しています。

新7診断の実装欠落は0で、状態不一致を含む仕様182件すべてが`CONFORMANCE`、警告0です。
